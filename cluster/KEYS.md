# Keys in a bridge node

What a host can see, where the bridge's signing keys live, how they survive a redeploy, how they are backed up and restored, and what was measured on a dev cluster. Nothing here is written for three nodes: n and k are `config.n` and `config.k` of the genesis, and every script reads them from there (`CLUSTER_SIZE` restates n and must agree).

## What the host sees

Everything. An Evernode instance is a container on the host's box; the host can read its filesystem and memory. On the dev cluster, `cfg/hp.cfg` holds the node's HotPocket identity **private key in plaintext** (`node.private_key`), next to the contract bundle and the consensus state. There is no enclave, no sealed storage. This is why no single host may hold k or more nodes (Decision 3 in `docs/DESIGN.md`): a bridge key on someone else's host is that someone's key.

## Where the bridge keys live

The contract's working directory is the consensus state directory (`contract_fs/mnt/state`, seeded from the bundle). Its parent, `../`, is served by the same hpfs mount but **is not part of the state hash**. everpocket keeps its signer key there (`../<master-address>.key`) and so will we. On an hpdevkit cluster `../` is `<volume>/node<N>/contract_fs/seed/`, and the volume is `/var/lib/docker/volumes/hpdevkit_<cluster>_vol/_data` on the host, with one `node<N>` directory per node, N = 1 to n.

| File | Contents | Consensus? |
|---|---|---|
| `./config.json`, `tokens.json`, `rounds.json`, `transfers.json`, `cursor.json`, `unmatched.json`, `treasury.json`, ... | Bridge state | Yes, byte-identical on every node |
| `./operators.json` | Every node's **public** XRPL and EVM keys, agreed over the NPL vote | Yes |
| `../bridge-keys.json` | This node's XRPL seed and EVM private key, generated by the node itself in its first consensus round, mode 0600 | No, node-local |
| `../bridge-payout.json` | Optional. `{"address":"r..."}`: where this node's payout share goes, if not its own key. Written by the operator, a public address, but wiped by a redeploy unless kept | No, node-local |
| `../bridge-node.json`, `../keys-seen.json` | Identity probe (node pubkey, first ledger, random nonce); public keys heard while the operator set formed | No, node-local |
| `/tmp/bridge-cluster.log`, `/tmp/bridge-last-round.json`, `/tmp/bridge-node.json` | Logs and the last round's vote summary | No, container-local |

Private halves never touch `./`. Public halves reach `./operators.json` only through the vote, like everything else that differs per node.

## Measured on the dev cluster

- `../` is non-consensus: each node wrote a different random nonce to `../bridge-node.json` in its first round and the three nodes kept closing ledgers with identical state hashes.
- `../` and `/tmp` survive a container restart (`docker restart hpdevkit_default_node_1`: same nonces before and after, cluster back in sync at the next ledger).
- Both are wiped by a redeploy on the dev cluster (`cluster sync` runs `rm -rf contract_fs/*`) and by lease expiry on Evernode. A redeploy that did not keep the keys would rotate them; a lost lease loses a signer.

## Surviving a redeploy

`scripts/deploy-dev.sh` keeps **every** node's `bridge-keys.json` and `bridge-payout.json` across the wipe (`scripts/remote/redeploy.sh`, the half that runs on the host):

- It stages the files of nodes 1 to n in a mode 0700 directory on tmpfs (`/dev/shm`, memory only), for the seconds between the wipe and the restore. n is the genesis's `config.n`, and the volume must hold exactly that many `node<N>` directories or nothing is touched.
- Before anything is stopped it checks the keys. A node with no key file while others have one **stops the deploy**, naming the node: a redeploy would give it a new random key and the SignerList would no longer match. `ACCEPT_NEW_KEYS=4,5` (or `all`) names the nodes that may start fresh, for a replaced node or the very first boot. A cluster with no key files at all is fresh on a test network and **refused on a mainnet genesis** unless `ACCEPT_NEW_KEYS=all`. An empty key file is a stop, not a missing one.
- The staged copies are shredded **only after every key is back on its node, non-empty and byte-identical**. If anything fails after the wipe (a failed `cluster sync`, a read-only disk) they stay in the staging directory, and the message names it and prints the exact command, `bash <dir>/RESTORE-KEYS.sh`, which restores, checks and shreds. The directory is memory: do not reboot before running it. The next deploy refuses to start while such a directory exists.
- The host half reads itself whole before it starts and ignores hangup and broken-pipe signals, so a dropped ssh connection or a Ctrl-C should not stop it between the wipe and the restore; it runs to the end and its log is `<remote dir>/redeploy.log`. If it is cut off anyway, the staged keys are still there and the next deploy says so.
- `hpdevkit-cluster.sh destroy` deletes the volume, keys included. It prints what is about to be lost, refuses the cluster named `main` and any cluster whose state or deployed genesis points at mainnet unless `CONFIRM_DESTROY=<cluster name>`, and `inspect` shows the same list without deleting anything.

## Backup and restore

A signing key is never copied anywhere in plaintext. The one allowed copy is **one encrypted file** made by `scripts/keys-backup.sh`, and it exists because a lost box, a lost lease or a bad day should not cost a signer.

**What to back up**

- Every node's `bridge-keys.json` and, where it exists, `bridge-payout.json`: all n nodes in one file. The script refuses to write a file that leaves a node out unless you name it (`ALLOW_MISSING_NODES`), and refuses a file that is not a bridge key file.
- Not in the file, kept by you: the recovery signer's key (a hardware key), the key the backup is encrypted to, and, until the master keys are disabled and the seeds deleted, `keys/<network>.json`.

**To what**

- To a recipient **public** key whose private half is held offline: a hardware key (an age plugin identity such as a YubiKey's, whose plugin binary must be installed on the host that encrypts, or an OpenPGP card) or a key kept on paper. Never a key that lives on a node host, and not the machine that runs the deploy scripts unless the key sits on a hardware token there. The script has no passphrase mode and no plaintext mode: with no recipient it writes nothing.
- `age` when installed (`BACKUP_RECIPIENT=age1...`, several allowed, or `BACKUP_RECIPIENTS_FILE`), otherwise `gpg --encrypt --recipient` with a full 40-hex fingerprint already in the host's keyring (`BACKUP_RECIPIENT=<fingerprint>`; a short id or an email is refused because it can name the wrong key). `BACKUP_TOOL=age|gpg` picks.

**How**

```bash
# on the node host, as root (copy scripts/keys-backup.sh there; it needs jq, tar and age or gpg)
DRY_RUN=1 BACKUP_RECIPIENT=age1... CLUSTER=main bash keys-backup.sh      # lists the nodes and addresses it would cover
BACKUP_RECIPIENT=age1... CLUSTER=main bash keys-backup.sh                # writes ./bridge-keys-main-<UTC time>.tar.age, prints its sha256 and the addresses
```

It prints the file's sha256 and, per node, the XRPL and EVM addresses it covers, never a key. It stages in tmpfs, writes `<file>.partial` and renames, and never overwrites an existing file.

**Where the encrypted file may live**

Anywhere that is not only the node box: a lost box would take the backup with it. It is ciphertext, so a second location (a laptop, a private cloud drive, a USB stick) is fine as long as the private key is not stored beside it. Keep the sha256 it printed somewhere else, in the ops log. Two copies in two places is the target.

**When**

After every event that creates or changes a node key: the first boot, a node replacement, a rotation. Keys do not change on a schedule, so there is no cron line for this. Then check it **the same day**, on a machine that holds the private key:

```bash
bash scripts/keys-restore.sh --verify bridge-keys-main-<time>.tar.age     # AGE_IDENTITY=<identity file> for age
```

`--verify` opens the file, checks that it holds exactly the paths a backup holds, that every seed derives the XRPL address on record and every private key the EVM address, that these match the manifest, and lists the addresses. It writes nothing. A backup you have not verified is a hope.

**Restoring**

```bash
bash scripts/keys-restore.sh bridge-keys-main-<time>.tar.age --out ./restored     # mode 0700; never over a non-empty directory
rsync -a --chmod=F600 ./restored/node4/ root@HOST:/var/lib/docker/volumes/hpdevkit_main_vol/_data/node4/
```

`./restored/node<N>/contract_fs/seed/` has the layout of the volume, which is what the deploy keeps and restores: after the rsync, `GENESIS=snapshot` or any redeploy carries the keys on. The restored files are plaintext; delete them (`shred -u` where you have it) when they are where they are going.

## The operator's own secrets (not the nodes' keys)

Five secrets are made on the operator's own machine and live in `cluster/keys/` (git-ignored, mode 600): the lock and funding accounts' seeds (`mainnet.json`, from `scripts/mainnet-accounts.ts new`), the Evernode tenant wallet's seed (`evernode-tenant.txt`, from `scripts/evernode-tenant.ts new`) the operator command key (`admin-mainnet.json`, from `scripts/admin.ts keygen`) and the upgrade key (`upgrade-mainnet.json`, the same tool; `UPGRADE_KEYS` at build time). Until a SignerList is set and the master key disabled, the first two *are* the locked funds; the tenant seed is the only way to extend or destroy the leased instances; the operator key sets caps, pauses and turns on the EVM side; the upgrade key can replace the cluster's code, which makes it the strongest of the four.

`npx tsx scripts/keychain-save.ts` copies them into the macOS login Keychain (and `... check` compares the two without printing anything). The Keychain is a second copy on the same machine, not an off-site one: keep an offline copy as well. The operator and upgrade items hold the 64-hex seed only (a terminal prompt takes about 127 characters and the whole key is 130): the key file is `{"privateKeyHex": "ed" + <seed> + <public key without its "ed">, "publicKeyHex": <public key>}`.

## What is safe to lose

| Thing | Safe? | Why |
|---|---|---|
| `/tmp` logs and caches, `bridge-node.json`, `keys-seen.json` | Yes | Rebuilt by the node; nothing depends on them |
| One node's consensus state | Yes | The other nodes hold it; a replacement node syncs it |
| The state of every node | **No**, unless backed up | It records which burns were paid. `scripts/state-backup.sh` copies it off the box (no secrets in it) |
| One node's `bridge-keys.json`, backup in hand | Yes | Restore it; without the backup the node is a lost signer |
| One node's `bridge-keys.json`, no backup | Costs a signer | Rotate the SignerList and the minter without it, starting now. Fine while n - 1 >= k, fatal beyond |
| More than n - k node keys, no backup, no recovery signer | **Lost for good** | The accounts can never be signed for again |
| `bridge-payout.json` | Annoying | Payouts fall back to the node's own XRPL address, which is still the node's key |
| The key the backups are encrypted to | **No** | Every backup becomes unreadable. Keep it offline, with a second copy |
| The recovery signer's key | **No** | It is the way back in when keys are lost |
| `keys/mainnet.json` (the lock and funding seeds) on the operator's machine | Delete it once both accounts have the SignerList and the master keys are disabled | Until then it is the only way to change the SignerList |

## Rules that follow

- A node's signing key is plaintext in exactly one place, its node. The staged copies of a redeploy live in memory for seconds, and the encrypted backup is the one allowed copy: a plaintext copy is a second signer nobody voted for.
- Losing a node means losing a signer. Rotation (`SignerListSet` with the survivors, k of n) starts the moment a node is lost, not when it becomes urgent.
- Choose k so that signing survives what consensus survives, and no minority can sign. HotPocket's own default closes ledgers with 80% of the nodes (ceil(0.8 n): 4 of 5, 3 of 3, 6 of 7), which with three nodes needs all three and stalls for good when one falls a ledger behind (seen on real Evernode hosts). So the cluster is created at the threshold where k nodes are enough (`scripts/lib/consensus.ts`: 66% for 2 of 3, 59% for 3 of 5; `docs/DESIGN.md` Decision 39), which makes consensus survive exactly what signing survives, n - k nodes down; k above n / 2 keeps a minority from signing and keeps two groups from both closing ledgers (the threshold is refused otherwise). n=5, k=3: two nodes can die and both signing and consensus continue, and an attacker needs three keys.
- A cold recovery signer on the lock and funding SignerLists (`RECOVERY_SIGNER`, weight k - 1 by default: useless alone, enough with any one node) is the way back from losing more than n - k node keys. It also means one node plus the recovery key can sign, so it lives on a hardware key and `scripts/testnet-signerlist.ts` says so every time it installs one.
- The HotPocket identity key (`hp.cfg`) and the bridge signing keys are unrelated. Rotating one does not touch the other.
- Read requests run the contract on a read-only snapshot; the key file is readable there too. Only the node itself runs that code.
- Script keys live in `keys/<network>.json` per XRP Ledger network (`XRPL_NETWORK`, devnet by default: `keys/devnet.json`, and `keys/testnet.json` for Testnet), gitignored, 0600, faucet money. Devnet may be reset without warning; the setup script funds fresh accounts and `GENESIS=devnet bash scripts/deploy-dev.sh` rewrites the genesis. Seeds are never printed and never pasted anywhere; mainnet signing is the operator's, by hand (`XRPL_NETWORK=mainnet KEYS_PATH=keys/mainnet.json`, which `testnet-setup.ts` refuses because it has no faucet). A relative `KEYS_PATH` resolves against `cluster/`, so seeds land under its gitignored `keys/` whatever directory the script is run from.
- The SignerList script reads the operator set from the cluster you point it at (`BRIDGE_QUERY`) and, on mainnet, refuses to run without one named explicitly, prints the signer set and the quorum before it asks, and asks twice before it disables a master key, because that cannot be undone.
